# 可编程填充系统

> [English](padding.md) | **中文** | [日本語](padding.ja.md)

## 概述

TSUNAMI 的可编程填充系统允许服务端控制隧道写入的分段与填充方式。填充方案通过 `cmdUpdatePaddingScheme`（`0x06`）从服务端推送到所有已连接的客户端，因此调整流量模式无需更新客户端。

填充是**按流（stream）、按方向**应用的：

- 每条被代理的连接（流）都会开始一个全新的填充周期（epoch）。即使一个 TLS 会话在数小时内承载了数千条代理连接，**每一条**流的内层 TLS 握手都会被掩盖，而不仅仅是第一条。
- 每个方向有各自的 writer 和规则。客户端掩盖其外发数据（SOCKS 目标地址、内层 ClientHello、应用数据）；服务端掩盖其外发数据（内层握手响应、应用数据）。
- 大多数规则使用 `~min-max` **pad-to（填充到）** 段：把整次写入作为**单个** TLS 记录发出，记录大小是 `[min, max]` 内一个合理的随机值，而不是把一次写入拆成多个大小做作的记录。
- 不属于单条数据流的帧（settings、SYN/SYNACK/FIN、心跳、填充方案更新、保活填充）在整个**会话生命周期内**都使用 `ctl` 规则，因此控制流量不会退化为固定大小的微小记录。

### 为什么需要可编程填充？

传统代理协议具有固定的数据包大小和时序模式，统计分析可以进行指纹识别。TSUNAMI 采用不同的方法：

- **服务端控制**：填充规则由服务端定义，而非客户端。调整在一个 RTT 内传播到所有已连接的客户端。
- **按流粒度**：每条流有独立的写入周期，因此每个内层握手都有各自的掩盖方式。
- **方向感知**：`c<idx>` / `s<idx>` 规则让同一份方案可以同时表达客户端握手序列和服务端握手序列。
- **运行时可更新**：服务端可以随时通过 `UPDATE_PADDING` 命令推送新方案，客户端立即应用。
- **空闲期伪装**：后台保活帧在空闲期间维持流量存在，防止“静默指纹”。

## 写入的分类

对每次隧道写入，填充 writer 首先判断它属于哪个桶（bucket）：

| 桶 | 条件 | 规则来源 | 周期 |
|:---|:-----|:---------|:-----|
| **数据流** | 所有帧都是 `cmdPSH`，且都携带相同的非零 stream ID | `<idx>`、`c<idx>`、`s<idx>` | 按流：每条新流重新开始 |
| **控制** | 其他所有情况：settings、SYN、SYNACK、FIN、心跳、填充方案更新、保活填充、stream ID 为 0 的帧，以及混合了命令/流的批次 | `ctl` | 无：会话生命周期内每次控制写入都使用同一规则 |

每条数据流每写入一次，周期推进一次：第 0 次写入使用规则 0，第 1 次使用规则 1，依此类推。当该流累计发出 `stop` 次写入或 `stream_bytes` 字节后，该流停止填充。流关闭时会被遗忘（`Session.SetOnStreamClosed` → `Writer.ForgetStream`），因此长会话不会累积状态，复用的 stream ID 也会重新开始周期。

控制桶没有周期：每次写控制帧时都会**重新**选择 `ctl` 规则，从而保证数据流周期结束后 SYN/SYNACK/FIN 与心跳仍被掩盖。

## 方案格式

填充方案是由换行符分隔的键值对文本块：

```
stop=6
stream_bytes=12288
ctl=~40-160
c0=~80-200
c1=~900-1200
c2=~500-1200
s0=~2600-4200
s1=~700-1400
s2=~700-1400
3=~300-800
4=~300-800
5=~300-800
keepalive=45000-90000:4-8
```

## 键

### `stop`

```
stop=<N>
```

**每条流**最多可被填充的数据写入次数（从 0 开始：写入 `0 .. N-1` 会查询规则）。该流的第 `N` 次及后续写入不做修改。

**默认值**：`6`

### `stream_bytes`

```
stream_bytes=<N>
```

按流的填充字节预算。当某条流累计写入的字节数达到该值后，该流的所有后续写入都不再做修改，与剩余的周期次数无关。这可以避免长时间的上传/下载在握手被掩盖之后仍持续承担填充开销。取值 `<= 0` 表示取消该预算。

**默认值**：`12288`

### 数据包索引规则

```
<index>=<segment>[,<segment>,...]
```

该索引处数据写入的共享回退规则。若该索引没有方向性覆盖规则，则两个方向都使用它。

### 方向性规则

```
c<index>=<segment>[,<segment>,...]    # 客户端 -> 服务端覆盖
s<index>=<segment>[,<segment>,...]    # 服务端 -> 客户端覆盖
```

方向性规则覆盖同一索引的共享规则。流写入的查找顺序为：**该索引的方向性规则 → 该索引的共享规则 → 不填充**。

客户端流的写入顺序：

1. SOCKS 目标地址帧（流的第一次写入），
2. 内层 TLS ClientHello，
3. 应用数据。

服务端流的写入顺序：

1. 内层 TLS 握手响应（ServerHello、Certificate 等），
2. 应用数据。

这就是默认方案掩盖客户端第 1 次写入（`c1=~900-1200`，ClientHello）和服务端第 0 次写入（`s0=~2600-4200`，服务端握手响应）的原因。

### `ctl`

```
ctl=<segment>[,<segment>,...]
```

应用于**每一次**控制写入（无流的帧和混合批次）的规则，在整个会话生命周期内生效。控制写入不受 `stop` 或 `stream_bytes` 限制。

**默认值**：`~40-160`

空值（`ctl=`）表示禁用控制写入的填充。

### `keepalive`

```
keepalive=<interval_min>-<interval_max>:<size_min>-<size_max>
```

配置空闲期后台保活数据包。当会话中的所有流都空闲时，服务端以随机间隔发送小的 `cmdWaste` 填充帧。

| 参数 | 描述 |
|:-----|:-----|
| `interval_min`–`interval_max` | 保活数据包之间的随机间隔（毫秒） |
| `size_min`–`size_max` | 随机保活载荷大小（字节）；记录本身仍会被 `ctl` 填充 |

**示例**：`keepalive=45000-90000:4-8` 在空闲时每 45–90 秒发送一个 4–8 字节的填充帧。

## 段类型

规则是由逗号分隔的段列表，按顺序应用：

| 类型 | 语法 | 描述 |
|:-----|:-----|:-----|
| 拆分范围 | `min-max` | 发出本次写入的下一块数据，大小在 `[min, max]` 内随机 |
| 检查 | `c` | 如果所有载荷都已消耗，停止发出段 |
| 填充到 | `~min-max` 或 `~N` | 把**剩余的全部载荷作为单个记录**发出，填充到 `[min, max]` 内随机的最小目标大小 |

### 拆分段（`min-max`、`c`）

对某条流的第 2 次数据写入使用 `2=400-500,c,500-1000,c,500-1000`：

1. 发出一个 400–500 随机字节的记录（先填真实数据，不足则填充）
2. **检查**：如果没有剩余载荷，停止 — 本次写入结束
3. 发出一个 500–1000 字节的记录
4. **检查**：如果没有剩余载荷，停止
5. 发出最后一个 500–1000 字节的记录

如果载荷长度超过所有段之和，剩余字节不做修改直接发出。拆分是旧版模式，仍然完全支持。

### 填充到段（`~min-max`）

`~900-1200` 把**整次**写入作为**一个** TLS 记录发出：

1. 在 `[min, max]` 中取一个随机目标大小。`~N` 表示恰好 `N..N`。
2. 把目标大小夹取到 `[len(payload)+7, 16384]`：
   - 下限为 `len(payload)+7`，保证记录内能放下一个 `cmdWaste` 帧头；
   - 上限为 `MaxPadTarget = 16384`，即 TLS 记录明文上限。
3. 如果载荷本身已经不小于请求的目标大小，则原样写出。载荷大到在记录上限内放不下 waste 帧头时也是如此。
4. 否则在同一次写入内追加一个 `cmdWaste` 帧，然后一次调用写出整个记录。填充到**永不拆分**写入。

填充到段会消耗剩余的载荷，因此 `~` 只有作为规则的最后一个段才有意义；同一规则中它后面的段会被忽略。

### 合理的记录大小

填充目标取自与同类流量真实 TLS 记录相近的分布：小的握手前导、约 1 KB 的 ClientHello、2.6–4.2 KB 的服务端证书序列，以及 0.3–1.2 KB 的应用数据记录。因此内层握手的精确大小不会再体现在外层记录大小中。

## 默认方案

```
stop=6
stream_bytes=12288
ctl=~40-160
c0=~80-200
c1=~900-1200
c2=~500-1200
s0=~2600-4200
s1=~700-1400
s2=~700-1400
3=~300-800
4=~300-800
5=~300-800
keepalive=45000-90000:4-8
```

此方案：

- 填充**每条**流的前 6 次数据写入（每条流独立周期），
- 掩盖客户端的 SOCKS 地址写入（`c0`）、内层 ClientHello（`c1`）和第一次应用数据写入（`c2`），
- 掩盖服务端的内层握手响应（`s0`）和最初的应用数据写入（`s1`、`s2`），
- 用共享规则 `3`、`4`、`5` 掩盖后续应用数据写入，
- 在整个会话生命周期内用 `ctl=~40-160` 填充每一次控制写入，
- 在空闲期间每 45–90 秒发送一个微小的保活帧。

规则基于索引，上面的尺寸假设了通常的写入顺序。如果客户端把 SOCKS 地址和最初的 TLS 字节放在一次 `Write` 调用中，则会使用 `c0` 处理这次合并写入；这是安全的，只是改变了哪条规则掩盖哪条记录。

## 方案版本控制

每个方案由其**原始文本的 MD5 哈希**标识。客户端在 `SETTINGS` 帧中包含当前的 `padding-md5`。如果服务端的方案不同，它会通过 `cmdUpdatePaddingScheme` 推送新方案。

这避免了在重连时不必要地重传未变化的方案。

## 线路协议

填充不引入新的帧类型，也不改变帧格式。线路协议不变，**无需提升协议版本**。

### 推送新方案

服务端发送 `cmdUpdatePaddingScheme`（`0x06`），帧数据为原始方案文本：

```
Frame {
    Command:  0x06 (UPDATE_PADDING)
    StreamID: 0
    Data:     <scheme text bytes>
}
```

客户端解析方案、计算其 MD5，并立即应用于所有后续写入；已有的按流周期保持不变。

### 填充帧

填充使用 `cmdWaste`（`0x00`）帧实现：

```
Frame {
    Command:  0x00 (WASTE)
    StreamID: 0
    Data:     <zero-filled bytes of specified size>
}
```

接收方必须读取数据并静默丢弃。填充帧数据有意使用零填充（而非随机）以最小化 CPU 开销 — TLS 层已经对其加密。一个填充后的记录可能包含一个真实帧加一个 `cmdWaste` 帧（pad-to），也可能是一次写入拆分出的多个记录（旧版拆分）。

## 兼容性与迁移

- **新客户端、旧方案文本。** 例如 `stop=8 / 0=30-30 / ... / keepalive=30000-60000:4-8` 的旧方案仍可解析。在新客户端上，`stop` 与数据规则按**每条流**解释（而不是按会话），并且由于旧文本没有 `ctl` 键，会应用隐式的 `ctl=~40-160` 规则。旧客户端会把同一文本按会话解释。
- **线路格式。** 填充只改变既有帧/记录的大小和数量，不改变其语法。无需提升协议版本。
- **混合版本与 `~`。** 新方案文本使用了旧解析器会忽略的键（`stream_bytes`、`ctl`、`c<idx>`、`s<idx>`），但旧解析器**无法解析**规则值中的 `~min-max` 段语法，会拒绝服务端推送的方案。因此新客户端会在 `SETTINGS` 帧中声明 `padding-v2=1`，服务端只向声明该能力的客户端推送 v2 方案文本：旧客户端不会收到无法解析的规则，它们继续使用自己的方案，隧道仍然可用（填充只是额外添加 `cmdWaste` 帧）。如果希望所有客户端统一切换到同一方案，请先升级客户端。
- 由于填充按方向应用，对端只需丢弃 `cmdWaste` 帧，两个使用不同方案的节点仍可通信；MD5 协商只是让支持相同语法的双方保持同步。

## 调优指南

| 场景 | 调整 |
|:-----|:-----|
| 高带宽服务器 | 增大 `stop`/`stream_bytes`；使用更大的 `~` 范围 |
| 低带宽/移动端 | 减小 `stop`/`stream_bytes`；使用更小的 `~` 范围 |
| 高安全环境 | 让 `~` 范围匹配真实 TLS 记录；提高 `ctl`；缩短保活间隔 |
| CDN 前置部署 | 让 `~` 目标匹配典型 HTTP/2 响应记录大小 |
| 旧版互操作 | 规则中避免使用 `~`；仅使用 `min-max` 拆分段 |

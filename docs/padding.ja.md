# プログラマブルパディングシステム

> [English](padding.md) | [中文](padding.zh.md) | **日本語**

## 概要

TSUNAMI のプログラマブルパディングシステムでは、サーバーがトンネル書き込みのサイズとパディングを制御できます。パディングスキームは `cmdUpdatePaddingScheme`（`0x06`）を通じてサーバーからすべての接続クライアントにプッシュされるため、トラフィックパターンの変更にクライアントの更新は不要です。

パディングは**ストリーム単位・方向単位**で適用されます：

- プロキシされる接続（ストリーム）ごとに新しいパディングエポックが始まります。1 つの TLS セッションが数時間にわたって数千のプロキシ接続を運んでも、**すべての**ストリームの内側 TLS ハンドシェイクがマスクされ、最初の 1 本だけに限定されません。
- 方向ごとに独自の writer とルールを持ちます。クライアントは送信データ（SOCKS 宛先アドレス、内側 ClientHello、アプリケーションデータ）をマスクし、サーバーは送信データ（内側ハンドシェイク応答、アプリケーションデータ）をマスクします。
- ほとんどのルールは `~min-max` **pad-to** セグメントを使用します。1 回の書き込みを**単一**の TLS レコードとして送出し、そのサイズを `[min, max]` 内の自然なランダム値にします。1 回の書き込みを不自然なサイズの複数レコードに分割することはありません。
- 単一のデータストリームに属さないフレーム（settings、SYN/SYNACK/FIN、ハートビート、パディングスキーム更新、キープアライブのウェイスト）は、**セッションのライフタイム全体**にわたって `ctl` ルールを使用します。そのため制御トラフィックが小さな固定サイズのレコードに退化することはありません。

### なぜプログラマブルパディングか？

従来のプロキシプロトコルは固定のパケットサイズとタイミングパターンを持ち、統計分析でフィンガープリントが可能です。TSUNAMI は異なるアプローチを取ります：

- **サーバー制御**：パディングルールはすべてサーバーが定義し、クライアントではありません。調整は 1 RTT 以内にすべての接続クライアントに伝播します。
- **ストリーム単位の粒度**：各ストリームが独自の書き込みエポックを持ち、内側ハンドシェイクごとに個別のマスクが得られます。
- **方向認識**：`c<idx>` / `s<idx>` ルールにより、1 つのスキームでクライアント側ハンドシェイクフライトとサーバー側ハンドシェイクフライトの両方を表現できます。
- **ランタイム更新可能**：サーバーは `UPDATE_PADDING` コマンドでいつでも新しいスキームをプッシュできます。クライアントは即座に適用します。
- **アイドル期間カモフラージュ**：バックグラウンドのキープアライブフレームがアイドル期間中もトラフィックの存在を維持し、「沈黙フィンガープリント」を防止します。

## 書き込みの分類

パディング writer は、トンネルへの各書き込みについてまずどのバケットに属するかを判定します：

| バケット | 条件 | ルール | エポック |
|:---------|:-----|:-------|:---------|
| **ストリーム** | すべてのフレームが `cmdPSH` で、すべて同じ非ゼロの stream ID を持つ | `<idx>`、`c<idx>`、`s<idx>` | ストリーム単位：新しいストリームごとにリセット |
| **制御** | それ以外すべて：settings、SYN、SYNACK、FIN、ハートビート、パディングスキーム更新、キープアライブのウェイスト、stream ID 0 のフレーム、コマンドやストリームが混在するバッチ | `ctl` | なし：セッションのライフタイム全体で毎回同じルール |

ストリームのデータ書き込みごとにエポックが進みます：書き込み 0 はルール 0、書き込み 1 はルール 1 を使用します。そのストリームが `stop` 回の書き込み、または `stream_bytes` バイトを送出すると、パディングは停止します。ストリームは閉じられると忘れられます（`Session.SetOnStreamClosed` → `Writer.ForgetStream`）。そのため長寿命セッションでも状態が蓄積せず、再利用された stream ID は新しいエポックから始まります。

制御バケットにはエポックがありません。制御フレームを書き込むたびに `ctl` ルールが選択されるため、データストリームのエポックが終了した後も SYN/SYNACK/FIN やハートビートがマスクされ続けます。

## スキームフォーマット

パディングスキームは改行区切りのキーバリューペアを含むテキストブロックです：

```
stop=6
stream_bytes=12288
ctl=~40-160
c0=~80-200
c1=~900-1200
c2=~500-1200
s0=~2600-4200
s1=~700-1400
s2=~700-1400
3=~300-800
4=~300-800
5=~300-800
keepalive=45000-90000:4-8
```

## キー

### `stop`

```
stop=<N>
```

**1 ストリームあたり**パディングできるデータ書き込みの最大数（0 始まり：書き込み `0 .. N-1` がルールを参照します）。そのストリームの `N` 回目以降の書き込みは変更なしで送信されます。

**デフォルト**：`6`

### `stream_bytes`

```
stream_bytes=<N>
```

ストリーム単位のパディングバイト予算です。あるストリームの累計書き込みバイト数がこの値に達すると、残りのエポック数に関係なく、そのストリームは変更なしで送信されます。ハンドシェイクがマスクされた後も長時間のアップロード/ダウンロードがパディングのオーバーヘッドを負い続けるのを防ぎます。`<= 0` は予算を無効にします。

**デフォルト**：`12288`

### パケットインデックスルール

```
<index>=<segment>[,<segment>,...]
```

そのインデックスのデータ書き込みに対する共有フォールバックルールです。そのインデックスに方向性ルールがない場合、両方の方向で使用されます。

### 方向性ルール

```
c<index>=<segment>[,<segment>,...]    # クライアント -> サーバー オーバーライド
s<index>=<segment>[,<segment>,...]    # サーバー -> クライアント オーバーライド
```

方向性ルールは同じインデックスの共有ルールを上書きします。ストリーム書き込みの検索順序は、**そのインデックスの方向性ルール → そのインデックスの共有ルール → パディングなし**です。

クライアントのストリーム書き込み順は次のとおりです：

1. SOCKS 宛先アドレスフレーム（ストリームへの最初の書き込み）、
2. 内側 TLS ClientHello、
3. アプリケーションデータ。

サーバーのストリーム書き込み順は次のとおりです：

1. 内側 TLS サーバーフライト（ServerHello、Certificate など）、
2. アプリケーションデータ。

デフォルトスキームがクライアントの書き込み 1（`c1=~900-1200`、ClientHello）とサーバーの書き込み 0（`s0=~2600-4200`、サーバーフライト）をマスクするのはこのためです。

### `ctl`

```
ctl=<segment>[,<segment>,...]
```

**すべての制御書き込み**（ストリームを持たないフレームおよび混在バッチ）にセッションのライフタイム全体で適用されるルールです。制御書き込みは `stop` や `stream_bytes` の制限を受けません。

**デフォルト**：`~40-160`

空の値（`ctl=`）は制御書き込みのパディングを無効にします。

### `keepalive`

```
keepalive=<interval_min>-<interval_max>:<size_min>-<size_max>
```

アイドル期間のバックグラウンドキープアライブパケットを設定します。セッション内のすべてのストリームがアイドル状態のとき、サーバーはランダムな間隔で小さな `cmdWaste` パディングフレームを送信します。

| パラメータ | 説明 |
|:-----------|:-----|
| `interval_min`–`interval_max` | キープアライブパケット間のランダム間隔（ミリ秒） |
| `size_min`–`size_max` | キープアライブのランダムペイロードサイズ（バイト）。レコード自体は `ctl` でパディングされます |

**例**：`keepalive=45000-90000:4-8` はアイドル時に 45–90 秒ごとに 4–8 バイトのウェイストフレームを送信します。

## セグメントタイプ

ルールはカンマ区切りのセグメントリストで、順番に適用されます：

| タイプ | 構文 | 説明 |
|:-------|:-----|:-----|
| 分割範囲 | `min-max` | 書き込みの次のチャンクを `[min, max]` バイトのランダムサイズで送出 |
| チェック | `c` | すべてのペイロードが消費された場合、セグメントの発出を停止 |
| Pad-to | `~min-max` または `~N` | **残りのペイロード全体を 1 つのレコードとして**送出し、`[min, max]` 内のランダムな目標サイズ以上にパディング |

### 分割セグメント（`min-max`、`c`）

ストリームの 2 回目のデータ書き込みに `2=400-500,c,500-1000,c,500-1000` を使用する場合：

1. 400–500 ランダムバイトのレコードを送出（実データを埋め、不足分はパディング）
2. **チェック**：ペイロードが残っていなければ停止 — 書き込み完了
3. 500–1000 バイトのレコードを送出
4. **チェック**：ペイロードが残っていなければ停止
5. 最後の 500–1000 バイトのレコードを送出

ペイロードがすべてのセグメントの合計より長い場合、残りのバイトは変更なしで送信されます。分割はレガシーモードで、引き続き完全にサポートされます。

### Pad-to セグメント（`~min-max`）

`~900-1200` は**書き込み全体**を**1 つの** TLS レコードとして送出します：

1. `[min, max]` からランダムな目標サイズを選びます。`~N` は正確に `N..N` を意味します。
2. 目標サイズを `[len(payload)+7, 16384]` にクランプします：
   - 下限 `len(payload)+7` は、レコード内に `cmdWaste` フレームヘッダーを収めるためです。
   - 上限 `MaxPadTarget = 16384` は TLS レコードの平文上限です。
3. ペイロードが要求された目標サイズ以上である場合は、そのまま送出します。レコード上限内でウェイストヘッダーの余地がない場合も同様です。
4. それ以外の場合は同じ書き込み内に `cmdWaste` フレームを 1 つ追加し、レコード全体を 1 回の呼び出しで送出します。Pad-to は書き込みを**分割しません**。

Pad-to セグメントは残りのペイロードを消費するため、`~` はルールの最後のセグメントとしてのみ意味を持ちます。同じルール内でそれ以降のセグメントは無視されます。

### 自然なレコードサイズ

Pad-to の目標サイズは、同じトラフィッククラスの実際の TLS レコードに似た分布から選ばれます：小さなハンドシェイクの前置き、約 1 KB の ClientHello、2.6–4.2 KB のサーバー証明書フライト、0.3–1.2 KB のアプリケーションデータレコード。したがって内側ハンドシェイクの正確なサイズが外側レコードのサイズに現れることはありません。

## デフォルトスキーム

```
stop=6
stream_bytes=12288
ctl=~40-160
c0=~80-200
c1=~900-1200
c2=~500-1200
s0=~2600-4200
s1=~700-1400
s2=~700-1400
3=~300-800
4=~300-800
5=~300-800
keepalive=45000-90000:4-8
```

このスキームは：

- **すべての**ストリームの最初の 6 回のデータ書き込みをパディングし（ストリームごとの独立したエポック）、
- クライアントの SOCKS アドレス書き込み（`c0`）、内側 ClientHello（`c1`）、最初のアプリケーションデータ書き込み（`c2`）をマスクし、
- サーバーの内側ハンドシェイクフライト（`s0`）と最初のアプリケーションデータ書き込み（`s1`、`s2`）をマスクし、
- 以降のアプリケーションデータ書き込みを共有ルール `3`、`4`、`5` でマスクし、
- セッションのライフタイム全体で `ctl=~40-160` によりすべての制御書き込みをパディングし、
- アイドル期間中に 45–90 秒ごとに微小なキープアライブを送信します。

ルールはインデックスベースであるため、上記のサイズは通常の書き込み順を前提としています。クライアントが SOCKS アドレスと最初の TLS バイトを 1 回の `Write` で送る場合、その結合書き込みには `c0` が使用されます。これは安全で、どのルールがどのレコードをマスクするかが変わるだけです。

## スキームバージョニング

各スキームは**生のテキストの MD5 ハッシュ**で識別されます。クライアントは `SETTINGS` フレームに現在の `padding-md5` を含めます。サーバーのスキームが異なる場合、`cmdUpdatePaddingScheme` を通じて新しいスキームをプッシュします。

これにより再接続時に変更されていないスキームの不要な再送信を回避します。

## ワイヤプロトコル

パディングは新しいフレームタイプを追加せず、フレーム形式も変更しません。ワイヤプロトコルは不変であり、**プロトコルバージョンの引き上げは不要**です。

### 新スキームのプッシュ

サーバーは `cmdUpdatePaddingScheme`（`0x06`）を送信し、フレームデータとして生のスキームテキストを含みます：

```
Frame {
    Command:  0x06 (UPDATE_PADDING)
    StreamID: 0
    Data:     <scheme text bytes>
}
```

クライアントはスキームを解析し、MD5 を計算し、すべての将来の書き込みに即座に適用します。既存のストリームエポックは保持されます。

### パディングフレーム

パディングは `cmdWaste`（`0x00`）フレームを使用して実装されます：

```
Frame {
    Command:  0x00 (WASTE)
    StreamID: 0
    Data:     <zero-filled bytes of specified size>
}
```

受信側はデータを読み取り静かに破棄する必要があります。ウェイストフレームのデータは CPU コストを最小化するため意図的にゼロ充填されます（ランダムではない）— TLS レイヤーが既に暗号化を行います。パディングされたレコードは、実フレームの後に `cmdWaste` フレームを含む場合（pad-to）と、1 回の書き込みを複数レコードに分割した場合（レガシー分割）があります。

## 互換性と移行

- **新しいクライアント、古いスキームテキスト。** `stop=8 / 0=30-30 / ... / keepalive=30000-60000:4-8` のような既存スキームは引き続き解析できます。新しいクライアントでは `stop` とデータルールが**ストリーム単位**で解釈され（セッション単位ではなく）、古いテキストには `ctl` キーがないため暗黙の `ctl=~40-160` ルールが適用されます。古いクライアントは同じテキストをセッション単位で解釈します。
- **ワイヤ形式。** パディングは既存フレーム／レコードのサイズと数のみを変更し、構文は変更しません。プロトコルバージョンの引き上げは不要です。
- **バージョン混在と `~`。** 新しいスキームテキストは古いパーサーが無視するキー（`stream_bytes`、`ctl`、`c<idx>`、`s<idx>`）を使用しますが、古いパーサーはルール値内の `~min-max` セグメント構文を**解析できず**、プッシュされたスキームを拒否します。そのため新しいクライアントは `SETTINGS` フレームで `padding-v2=1` を通知し、サーバーはその能力を通知したクライアントにのみ v2 スキームテキストをプッシュします。旧クライアントには解析できないルールが送られず、各自のスキームを使い続けます（パディングは `cmdWaste` フレームを追加するだけなのでトンネルは動作します）。すべてのクライアントを同じスキームに揃えたい場合は、先にクライアントをアップグレードしてください。
- パディングは方向ごとに適用され、相手側は `cmdWaste` フレームを破棄するだけでよいため、異なるスキームを持つ 2 つのピアでも通信できます。MD5 ネゴシエーションは同じ構文をサポートする双方を同期させるだけです。

## コメント

`#` で始まる行はコメントとして扱われ、無視されます：

```

c1=~1000-1400
0=~400-1000
1=~400-1000
2=~400-1000

```

## チューニングガイドライン

| シナリオ | 調整 |
|:---------|:-----|
| 高帯域幅サーバー | `stop`/`stream_bytes` を増やし、`~` の範囲を大きくする |
| 低帯域幅/モバイル | `stop`/`stream_bytes` を減らし、`~` の範囲を小さくする |
| 高セキュリティ環境 | `~` の範囲を実際の TLS レコードに合わせ、`ctl` を上げ、キープアライブ間隔を短くする |
| CDN フロントデプロイ | `~` の目標を典型的な HTTP/2 レスポンスレコードサイズに合わせる |
| レガシー相互運用 | ルールで `~` を使わず、`min-max` 分割セグメントのみを使用する |
